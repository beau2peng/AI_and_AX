# I Asked an AI to Do Some Addition—and Ended Up Rebuilding the Search API

While building a Search API for AITOOL that lets users query internal database information in natural language, I ran into an unexpectedly interesting problem. The original idea was fairly simple: let the AI understand the user's request, search the database using the appropriate conditions, and then turn the results into a readable answer. To avoid sending personal information to the AI, I created a separate View containing only the fields needed for statistics, and the server returned only aggregated results based on the search conditions generated by the AI.

For example, if a user asks, "Show me the number of enrolled and on-leave students by department as of April 1, 2026," the LLM determines the reference date, enrollment status, department, and other conditions. It turns those conditions into JSON that follows the Search API specification, Oracle DB aggregates the matching student counts, and the LLM explains the results in a human-friendly way. In the first tests, it was surprisingly good at translating natural-language requests into search conditions, so I was pretty happy with it.

The architecture itself was not complicated. The LLM converted the user's question into a Search API request, the server queried Oracle DB and returned the result, and the LLM produced the final answer. Looking back, there was a small problem hiding in this design, but at the time I did not think much of it.




![Search_Tool_Diagram](images/search_diagram_before.png)


## The Numbers from the DB Were Right, but the Total Was Wrong

As I expanded the Search API, I started testing queries that returned multiple rows along with an overall total. For example, Oracle would return a `COUNT` for each department, and the LLM would explain the department-level numbers and, when needed, provide the grand total. Since the database had already returned all the correct numbers, I assumed asking the LLM to add a few of them together would be harmless.

Then repeated testing started producing something strange. Every individual row returned by the Search API was correct, but the overall total in the final answer from Qwen3.6 27B was occasionally wrong. My first suspicion was the Search API or the SQL, so I ran the query directly against the database and checked the API response again. The individual values were fine.

At first, I wondered whether I had simply added the numbers incorrectly myself, so I copied them into Excel and checked again. At that point I still did not really expect an LLM to keep getting such a simple sum wrong, so I was more suspicious that the Search API had dropped something along the way. But Excel's `SUM` result and Qwen's total were, in fact, different.


### [Actual Screen 2 - Cross-checking in Excel]

![Search_Tool_Diagram](images/calc_error1_check.png)


Sometimes asking again produced the correct total, while a different dataset would fail again. The more rows there were, the harder it became to trust the result. The AI was perfectly capable of understanding a natural-language request, turning it into search conditions, and calling an API—yet somehow it could still stumble over adding a handful of numbers at the very end. That was both frustrating and, admittedly, a little funny.






## Naturally, I Tried Fixing the Prompt First

My first idea was, of course, to fix the prompt. I added instructions such as "Add the values in each row accurately" and "Verify the total before returning the answer." It even looked a little better for a while. But after a few more tests, the wrong totals came back.

So I tried something else. I happened to have Qwen3 14B running on another machine, and I thought: what if I let Qwen3 14B verify the result produced by Qwen3.6 27B? I sent it both the original data and Qwen3.6's answer, with a prompt telling it to check the sum and return a corrected result if the total was wrong.

It sounded reasonable enough. If the first LLM made a mistake, perhaps a second LLM calculating the numbers independently could catch it. In effect, I had added another model as a Reviewer or Validator. Surely, I thought, double-checking simple addition twice should improve things.

**Nope. That one did the same thing.**

![Search_Tool_Diagram](images/search_diagram_1.png)




I asked Qwen3 14B to verify Qwen3.6 27B's incorrect calculation and fix it if necessary, and there were still cases where the resulting total was wrong. I had added another model, another call, and another prompt, but the one thing I actually needed—numerical correctness—still was not guaranteed.

At this point, the architecture started to look a little ridiculous. I was asking one AI to add the numbers, then sending the same numbers to a second AI on another machine because I did not trust the first one, and finally hoping that at least one of them would get it right. For statistical data, "usually correct" is not good enough, yet I was trying to improve accuracy by performing the same probabilistic calculation one more time.

Even if the result is correct 99 times out of 100, one wrong number in an important report means somebody still has to verify everything. At that point, I would have built a natural-language Search API to save work, only to make someone open Excel again and check the totals manually. And that led to a very basic question.

**Why was I making two LLMs take turns doing addition when Oracle DB was sitting right next to them?**

Oracle could solve the problem exactly with a single `SUM()`. Qwen3.6 getting the calculation wrong—and Qwen3 14B failing to reliably catch it—was what exposed the issue, but the more fundamental problem was the architecture itself: I had assigned a probabilistic model a calculation whose result had to be deterministic.





## I Reassigned the Jobs: AI Does AI Work, the DB Does DB Work

I am still quite happy with Qwen3.6 27B when it comes to understanding natural-language requests and deciding what needs to be searched. Given a request such as "Show me how the number of enrolled students by department has changed over the last five years," it can interpret concepts such as `last five years`, `by department`, `enrolled students`, and `change`, then determine the search conditions it needs. Compared with the traditional approach of building a separate screen and a pile of search options for every report, that is a genuinely interesting shift.

Accurately adding numbers that have already been retrieved, on the other hand, does not require natural-language understanding or reasoning. There is one correct answer, and the same input should always produce the same output. So I divided the responsibilities again: the LLM would understand user intent and decide what work was needed, while the server and database would handle retrieval and calculations where correctness had to be guaranteed.

![Search_Tool_Diagram](images/search_diagram_2.png)





## I Moved the Total into a Separate Rollup

The first change was straightforward: stop asking the LLM to calculate the grand total. The Search API still retrieves the detailed rows as before, but conditions that require an overall total are separated out and aggregated again on the server using `SUM`. That value is returned as a Rollup alongside the detailed rows. The LLM receives both the rows it needs for explanation and a total that the server has calculated deterministically.

So even when a query returns many department-level rows, the LLM no longer adds them together. It uses the rows to describe each department and uses the value in the Rollup whenever it needs the overall total. Once the responsibility for arithmetic moved back to the database, there was no longer any need to keep tweaking prompts or asking the LLM to verify its own calculation.

![Search_Tool_Diagram](images/search_diagram_3.png)


That solved the original sum problem. But as I kept testing the Search API with Rollup in place, another issue became more obvious—something I had not paid much attention to in the original design. A natural-language question does not necessarily map to exactly one Search request.





## One Question Does Not Necessarily Mean One Search

The first version of the Search API handled one search per request. For a clear question such as "Show me the number of enrolled students by department for the first semester of 2026," that was perfectly adequate: run one Search and return the result. At the beginning, the more important goal was simply proving that one Search API specification could replace a number of existing statistical queries.

But a request such as "Compare the number of enrolled students by department over the last few years and also show how the overall student population changed" is different. If one set of search conditions cannot answer the whole question, the LLM has to issue the first Search, receive its result, then issue another Search. As the number of required queries grows, the LLM ends up managing not only the searches themselves but also intermediate results and what needs to happen next.

![Search_Tool_Diagram](images/search_diagram_4.png)


After fixing the Rollup problem, I looked at this flow and had a similar thought. Just as there was no good reason to make the LLM perform arithmetic that the server could handle more reliably, did the LLM really need to manage the execution order and result collection for a set of searches that had already been decided? Instead of having the LLM immediately execute each Search, I decided to make it plan the entire job first.





## Instead of Running Searches One by One, I Asked for an Execution Plan

When a user request requires multiple queries, the LLM now creates the full execution plan instead of immediately running each Search. The required Search requests are placed into a Queue and sent to an Executor in one batch. The Executor runs the queued requests through the actual Search API and collects the results. From the LLM's perspective, its job is to decide what data is needed; actual execution and result collection belong to the server.

This means that whether the request needs one Search or five, the LLM no longer has to bounce back and forth with the Search API for every step. The Executor follows the plan, performs the work, combines everything into a single Result Package, and returns it to the LLM. This structure also gives me a much cleaner place to add retry logic, result checks, and other execution-level safeguards later.

![Search_Tool_Diagram](images/search_diagram_5.png)





## Rollup Became Part of the Executor's Result as Well

Once the Executor existed, it made sense to fold the Rollup logic into the same execution process. When an Execution Plan contains multiple Search requests, the Executor runs each one and gathers the results. Conditions that can be aggregated with `SUM` are separated out, the database calculates the overall totals again, and those Rollup values are packaged together with the individual Search results.

What reaches the LLM in the end is therefore more than a pile of database rows. It receives both the detailed search results requested by the user and totals that the server has calculated accurately. The LLM can compare the values, interpret them, and explain what they mean without ever having to add dozens of numbers itself.

![Search_Tool_Diagram](images/search_diagram_6.png)


I originally thought I was just building a natural-language interface for querying a database. By this point, however, the responsibilities had changed quite a bit. The LLM was no longer calling Search operations one at a time. It was breaking the user's request into executable units and producing a plan, while the server-side Executor carried out that plan. And calculations that required guaranteed accuracy were no longer dependent on the LLM at all.





## I Fixed One Addition Problem and Somehow Ended Up Building an Executor

The original problem really was that simple: Qwen3.6 27B would receive perfectly correct numbers from the database and occasionally produce the wrong total at the end. I initially assumed a better prompt would fix it. Following that problem, however, forced me to ask why I had assigned exact arithmetic to the LLM in the first place, which eventually led to the Rollup.

Once Rollup was in place, a similar question appeared. If multiple Searches were needed, why was the LLM responsible for managing the execution process one call at a time? That question eventually produced the Execution Plan, Queue, and Executor. I started out trying to fix some addition and ended up changing the execution architecture of the Search API.

![Search_Tool_Diagram](images/search_diagram_after.png)


Even after years of development, this kind of thing still happens. You start by assuming a particular piece of code or a model is the problem and try to patch that spot. Then, if you follow the problem far enough, you sometimes discover that the real issue is not a bad line of code at all—it is the way responsibilities were divided between the components in the first place. This time, Qwen's arithmetic mistake happened to expose exactly that kind of design problem.





## Instead of Making the AI Never Wrong, Make the System Stay Correct

This experience reminded me that deciding what *not* to ask an LLM to do can be just as important as deciding what else to give it. LLMs are very good at interpreting ambiguous natural language, figuring out what a user actually wants, and turning a collection of results into an explanation that people can understand. Those abilities make it possible to handle requests that would previously have required dedicated screens, predefined filters, and a lot of application code.

But a total is different. When there is one correct answer and correctness matters, there is no reason to make the LLM responsible for it. If the database can do something more accurately, let the database do it. If a fixed execution plan simply needs to be carried out in order, let the Executor do it. The LLM can sit above those layers and focus on understanding the request and deciding what needs to happen.

As models improve, simple arithmetic errors like this will probably become much less common. Larger models may already perform better, and at some point they may almost never get these sums wrong. Even then, I do not think I would remove the Rollup and hand the totals back to the LLM. A model being capable of calculating something and a production system being able to guarantee the correctness of that calculation are two different things.

This all started because I added a few numbers, thought the result looked suspicious, and opened Excel to check them. Following that tiny error led to a Rollup, then to a rethink of how multiple Searches should be executed, and eventually to an Executor. None of that was part of the original plan, but it ended up giving AITOOL a much clearer division of responsibilities between the LLM and the server.

**The lesson from this particular detour was not to demand that the AI always be right. It was to design the system so that even when the AI is occasionally wrong, the system's result does not have to be.**




Now that the totals come out right every time, I can finally relax a little.
